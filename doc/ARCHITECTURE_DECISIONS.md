## Решения от 25.09.2026 (по итогам обсуждения открытых вопросов)

### Р1. Машина DAQ-сервера — принято

- **Лаборатория (тесты сейчас):** `server.danss.local`, Fedora 33, системный GCC 10 (для C++20 недостаточно). MIDAS собирается так же, как на cvme1: conda-тулчейн GCC 13 в `$HOME`, статический libstdc++, коммит `c69c0853930b226e96090725a0ba5cb2b4293a14`.
- **Эксперимент:** можно запросить Ubuntu 24.04 — там достаточно системного GCC 13, conda не нужна. Коммит MIDAS тот же, что на всех остальных машинах.

### Р2. Вычитывание WFD — по Ethernet, принято

- Все модули WFD отдают данные **по 1 Гбит Ethernet (UDP) через switch на DAQ-сервер**.
- Следствия:
  - процесс вычитывания WFD работает **на DAQ-сервере**, а не на крейте (уточнено в Р6: на отдельном сервере event builder'а);
  - на `cvme1` остаётся только **настройка модулей через VME** (регистры, тактовая, триггер, запрет); крейт становится «тонким»;
  - нужна отдельная сеть/switch для WFD и сетевой интерфейс под неё на сервере;
  - протокол UDP у модуля — запрос/ответ (сервер сам запрашивает чтение FIFO и двигает `FIFO_RADDR`), поэтому потерянный ответ можно перезапросить.
- Уточнить: противоречие в `wfd_description.pdf` (таблица передней панели: Ethernet «пока не реализован»; раздел 4.10: UDP с прошивки 2.5) — проверить на железе, какая прошивка залита (в репозитории есть `main_v2.6.bin`).

### Р3. Сборка событий — свой event builder, принято

- Отдельный event builder собирает события из записей всех модулей **по токену** (10 бит + метки типа 5 на токенах 0/256/512/768), между вычитыванием и `mlogger`.
- Стандартный `mevb` не используется: он собирает фрагменты по номеру события frontend'а, а поток WFD связан только токеном, порядок записей не гарантирован, модуль без сработавших каналов молчит.
- Открытые детали реализации: окно ожидания по токену, обработка потока самозапуска (тип 0, к триггерам не привязан), поведение в зависимости от типа рана (см. вопрос 6).

### Р4. Slow Control — на отдельной машине, принято

- SC-frontend'ы (SlowControl по Modbus, PowerSupply, RunSync) работают **на отдельной SC-машине**; требования к ней может выдвинуть наша сторона.
- Требования (черновик, сформулировать отдельно): число портов RS-485 под 4–8 веток, сеть до OWON (`192.168.10.81`, порт 3000) и до DAQ-сервера (`mserver`), ОС (Ubuntu 24.04 → системный GCC 13), синхронизация времени с DAQ-сервером, ИБП.

### Р5. Настройки WFD — в ODB, принято

- Источник настроек WFD — ODB: общие параметры + переопределения по модулям (аналог секций `Def` / `DevNNN` в `general.conf`).
- Существующий `general.conf` импортируется в ODB скриптом.

## Решение совещания (начало октября 2026)

### Р6. Event builder — на отдельном сервере, принято

- Event builder, собирающий события со всех плат WFD (и VME), работает **на отдельном сервере и занимается только сборкой событий**.
- Основной MIDAS (ODB, `mserver`, буфер событий, `mlogger`, `mhttpd`, история, алармы) — на другой машине.
- Цель: максимальная скорость сборки — приём UDP и сопоставление по токену не делят CPU, память и сетевой интерфейс с логгером, веб-интерфейсом и анализом.
- Итого машин в схеме: cvme1 (настройка WFD по VME) · сервер event builder'а (приём UDP + сборка) · основной MIDAS-сервер (ODB, logger, веб) · SC-машина.

Замечания и рекомендации к реализации (обсуждено с Claude, не все приняты):
- Буфер событий и ODB MIDAS живут в общей памяти основного сервера; event builder на другой машине — удалённый клиент, собранные события уходят в буфер через `mserver` по TCP. Данные проходят сеть дважды: модули → EB (UDP), EB → основной сервер (TCP). Канал EB → основной сервер должен быть с запасом по пропускной способности (рекомендация: 10 Гбит, отдельный интерфейс от сети модулей).
- Естественно оформить event builder как **MIDAS-frontend** (Equipment с собранными событиями): переходы ранов, настройки из ODB, статистика и мониторинг в `mhttpd` — без своего протокола.
- Протокол UDP модуля — запрос/ответ, а у модуля 512 МБ SDRAM: если EB или канал до логгера не успевает, данные ждут в памяти модулей, а не теряются. Это даёт естественное «обратное давление».
- Сначала оценить поток: размер события × частота триггера + поток самозапуска (тип 0). От этого зависят требования к сетям, диску основного сервера и самому серверу EB.
- На сервере EB: увеличенные буферы приёма UDP в ядре, при необходимости привязка потоков к ядрам CPU; время синхронизировано с остальными машинами (chrony).

## Открытый вопрос 6: смена режимов Physics ↔ Calibration

**Понимание пользователя (25.09.2026):**
- раны меняются **автоматически**, без участия оператора;
- event builder знает текущий тип рана и в зависимости от него собирает события или не собирает;
- после калибровочного рана выполняется **калибровка и оптимизация gain и напряжения на SiPM**, затем продолжается физический ран.

То есть это замкнутый цикл: калибровочный ран → обработка → новые уставки HV/DAC → SC применяет → физический ран.

Вопросы, которые из этого следуют (не решены):
1. **Кто ведёт автоматическую последовательность ранов:** секвенсор MIDAS (`msequencer`) или собственный процесс-супервизор. От этого зависит, как цикл ждёт окончания калибровочной обработки.
2. **Где и как идёт калибровочная обработка:** онлайн-анализатор на DAQ-сервере? Сколько она длится, что на выходе (gain по каналам → уставки HV/DAC), в каких единицах.
3. **Безопасность автоматических уставок:** ограничения на шаг и абсолютные значения HV, откат к прежним значениям при неудачном фите, нужно ли подтверждение человека.
4. **Прослеживаемость:** набор уставок, с которыми набран каждый ран, должен сохраняться (ODB-дамп в файле рана + история версий уставок).
5. **Поведение event builder по типу рана:** в калибровке — не собирать, собирать иначе (события по LED-триггеру) или писать поканальные записи.
6. **Мёртвое время:** изменение HV требует плавного подъёма; физический ран стартует только после подтверждения SC, что всё стабилизировалось.

Предложенная ранее база (не принята): тип рана хранится в ODB, переходы ранов MIDAS с приоритетами (SC/питание получают старт раньше WFD, отказ любого участника отменяет старт), HV между ранами не выключается, MAINTENANCE — флаг в ODB, блокирующий старт.

## Решения ноября 2026

### Р7. Frontend'ы — отдельные программы на TMFE, принято (02.11.2026)

- Каждая подсистема SC — **своя программа**: `danss_psu_fe` (блок питания, готов), SlowControl
  для плат (следующий шаг). Сбой опроса плат не мешает управлению HV и наоборот.
- Используется современный C++ API MIDAS **TMFE** (`tmfe.h`); старый `mfe.cxx` не используется
  (`libmfe.a` приносит второй `main()`).
- Долгие операции (разгон HV до 55 В ≈ 1 мин) — в своём потоке (`PsuWorker`); периодический
  обработчик и RPC MIDAS не блокируются.

### Р8. Настройки блока питания — в ODB с проверкой, принято (02.11.2026)

- При первом запуске `/Equipment/PowerSupply/Settings` заполняется из `power_supply.json`,
  дальше правится в mhttpd. **Каждое изменение проверяется `ConfigLoader`** (пределы ODP6033,
  OVP выше цели, OCP не ниже тока, интерлок для SIPM_HV); недопустимое отклоняется целиком,
  действуют прежние настройки, ошибка — в `Readback/Settings error` и аларм.
- Команды — `Settings/Enable[3]`; при неудаче сбрасываются в `n`. Перезапуск frontend выходы
  не переключает.

### Р9. Интерлок HV — пока ручной флаг в ODB, принято (02.11.2026)

- `Settings/Interlock ready`, при старте frontend `n`. Целевой источник — SlowControl по
  состоянию плат (на связи, `Update#` растёт, нет trip, температуры в норме); условия и
  реакция на каждое нарушение — **решение группы до подключения SiPM** (открыт).
- Интерлок — программный флаг, не аппаратная защита (её дают OVP/OCP прибора) и не страховка
  от падения программы.

### Р10. Блок питания — по IP, управление выходами по каналам (02.11.2026)

- В конфигах `192.168.10.81`, не `d2pwr1.danss.local`: на cvme1 Boost.Asio не разрешает имена `.local`.
- `OUTPut:STATe` у ODP6033 переключает **все** каналы; один канал — только `CHANnel:OUTPut:ALL`
  с обратным чтением. Аварийное выключение — `OUTPut:STATe 0`. OCP максимум 3.1 А.

### Р11. Платы — 38400 бод, карта регистров v2 (07.11.2026)

- Скорость 38400 8N1 на всех платах (подтверждено); `DEFAULT_BAUD_RATE` и конфиги переведены.
- Работа с платой — через `BoardClient`; утилита `modbus_tool`. Сверка DAC и алармы по
  температуре — только для подключённых аналоговых плат (признак — ждём ответа Игоря).
- Scratchpad загружается сам при включении питания — SlowControl после сбоя питания команду
  101 не подаёт, но фиксирует перезагрузку по сбросу счётчика input 0.

### Р12. Управление платами — через тот же danss_sc_fe, принято (07.11.2026)

- RS-485 — полудуплекс с одним мастером: **кто владеет портом ветки, тот и пишет** на её
  платы. Отдельного frontend'а для управления нет (два процесса на одном порту перемешали бы
  кадры). Блок питания — отдельно (`danss_psu_fe`): свой прибор и своё TCP-соединение.
- Схема (задача s2-07): желаемое — `Settings/Boards/<имя>/` (DAC[96], HV enable, Gain trip
  enable, Cycle delay; как Demand в классическом SC MIDAS), фактическое — `Boards/<имя>/` по
  обратному чтению (Measured). Расхождение → команда в очередь ветки, её выполняет поток
  опроса между циклами; результат — `Last write`, журнал, при неудаче аларм. Flash (103→105) и
  загрузка — флаги ODB и JRPC. Первый запуск: уставок в ODB нет → читать с платы, не писать.
- `modbus_tool` — сервисная утилита при остановленном frontend (адрес, первичная настройка).
- Открыто: набор уставок; эталон (предложение — ODB, `eeprom_reference.json` для суточной
  сверки); восстановление после перезагрузки платы; flash по команде или сам; изменения во
  время рана.
